Model Speed-to-Answer

Every hour, each model gets the same byte-identical prompt — write a program to solve a non-trivial counting problem — and we time the response. Nothing is executed and nothing is graded; the number is how long you wait for an answer, verbosity included.

How this works

The whole method, in four steps. Everything below is public — github.com/bsxp/llm-heartbeat.

STEP 1
One fixed prompt
Every model gets the identical prompt — write a program to solve a counting problem. A hash of it (—) is recorded on every run, so if it ever changes you can see exactly where the series breaks.
STEP 2
Same settings, every time
Reasoning effort and thinking mode are pinned per model and written onto every row. Both change latency, so leaving them to defaults would make one model look slower for reasons that have nothing to do with the model.
STEP 3
We time the stream
One streaming request per model, on a schedule. A clock starts before the request, stamps the first visible word, and stops when the response ends. Nothing is executed and nothing is graded.
STEP 4
Plotted as-is
No averaging across runs, no normalising for length. If a model wrote more and therefore took longer, that is the number — because that is the wait.

Everything between the two marks is counted — including network round-trip and any queueing on the provider’s side. We measure from outside, so we cannot separate “the model was slow” from “the network was slow” from “we were queued”, and we don’t claim to. Runs execute from a single AWS region, which keeps that overhead roughly constant — so the changes are meaningful even though the absolute numbers carry a fixed tax.

What each number means

Total time
Request sent to response finished — the headline. Includes however much the model chose to write. Given an identical prompt, a wordier model genuinely does make you wait longer, and we don't correct for that.
First token
How long until the first visible word. This includes reasoning time — models that think before answering are silent for this entire stretch. It is not a network-latency figure.
Delivery rate
Output tokens ÷ the writing phase. Not a generation speed. Some providers reason silently and then flush the whole answer at once, which shows up here as an implausibly high rate — it is measuring how fast a finished buffer arrives, not how fast the model writes. Compare it within a model over time, not between vendors.
Output tokens
How much the model wrote. Same prompt every time, so this is its own verbosity — and it is most of what drives total time. Not comparable across Anthropic generations: Opus 4.7 changed tokenizers, so the same text counts higher on 4.7+ than on 4.6.
Health
A sanity flag — did a plausible answer come back at all. Not a grade. Nothing runs the code. It exists so a spike can be told apart from a refusal or an empty response, which are excluded from the charts rather than plotted as fast runs.
