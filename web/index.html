How this works

Every model gets the same prompt, on a schedule, and we time the reply. Nothing is executed and nothing is graded — this measures the wait, not the answer.

  • One fixed prompt. A hash of it (—) is stored on every run, so a change to it is visible instead of silent.
  • Settings are pinned. Reasoning effort and thinking mode are fixed per model and recorded, because both change latency on their own.
  • Nothing is smoothed. No averaging, no adjusting for length. A model that wrote more really did take longer.

Everything between the two marks is counted — including network round-trip and any queueing on the provider’s side. We measure from outside, so we cannot separate “the model was slow” from “the network was slow” from “we were queued”, and we don’t claim to. Runs execute from a single AWS region, which keeps that overhead roughly constant — so the changes are meaningful even though the absolute numbers carry a fixed tax.

What each number means

Total time
Request sent to response finished — the headline. Includes however much the model chose to write; a wordier model genuinely does make you wait longer, and we don't correct for that.
First token
How long until the first visible word. Includes reasoning time — models that think before answering are silent for this whole stretch.
What we don't measure
Correctness, quality, or capability. Nothing runs the code. The health flag only separates a slow run from a refused or empty one — it is not a grade.

All models

Medians across the selected range. Two caveats that don't fit in a column: rate is not generation speed for models that reason silently then flush the whole answer at once, and output tokens aren't comparable between Opus 4.6 and 4.7+ (different tokenizers). Every model runs at medium effort with adaptive thinking.
